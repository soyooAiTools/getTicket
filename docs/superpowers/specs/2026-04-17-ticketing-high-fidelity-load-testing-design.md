# 票务高保真压测方案设计说明（历史归档）

> 这份设计稿对应 SaaS 重构前的早期产品定义，现已被后续的 Load-Testing SaaS 方案替代。保留此文档是为了记录“为什么团队会从普通压测工具，走向受控、高保真的抢票压测闭环”。

## 背景

这份设计最初定义的是一套面向内部、且经过授权的高保真压测系统，用于验证抢票窗口期的真实压力行为。它关注的不只是通用 benchmark，而是三类更贴近业务的真实性：

1. 多地域网络时延真实性
2. 排队、库存、下单链路的业务并发真实性
3. 多节点协同起压时的峰值并发真实性

当时达成的共识是：

- 以预发环境为主压测环境
- 以线上受控观察和白名单灰度验证作为校准手段
- 最终目标是建立预发与线上之间的统一校准闭环

## 已确认范围

早期方案批准的范围包括：

1. 独立控制面，用于编排任务与汇总结果
2. 多地负载节点，其中香港为锚点区域
3. 面向发售窗口的阶段化流量建模，而非平铺直叙的 benchmark 流量
4. 预发大规模回放与压测
5. 线上受控观察与限制性校准
6. 统一评分与校准回路
7. 对线上验证 run 的隔离标签、隔离账号与隔离报表

## 目标

本设计期望达成：

1. 在预发环境中足够真实地复现发售窗口压力
2. 测量不同地域网络条件对排队、库存锁定与下单成功率的影响
3. 对比锚点节点与边缘节点在同一窗口下的行为差异
4. 量化预发结果与线上结果之间的偏差，并反向修正下一轮测试模型
5. 给团队一条受控的线上校准路径，而不是无约束地对真实业务施压

## 非目标

这个早期方案明确不追求：

1. 覆盖所有对抗式攻击技术的红队系统
2. 对真实库存进行无约束的线上压力测试
3. 第一阶段就交付完整功能齐全的控制台
4. 面向终端用户的任何产品能力
5. 在闭环尚未验证前，就为所有未来业务线做通用容量平台

## 方案价值

虽然这份设计已经被归档，但它留下的几个判断后来都进入了当前 SaaS 版本：

1. 压测必须围绕业务真实链路，而不是只看 HTTP QPS
2. 多节点与多区域建模是这类系统的核心价值之一
3. 预发压测与线上受控校准必须属于同一闭环
4. 控制面、Agent、报告模型必须独立于被测业务系统存在

## 与当前版本的关系

当前主交付版本已经不再沿用“ticketing platform 附带压测系统”的叙述，而是明确转向：

- `主产品`：内部 Load-Testing SaaS
- `控制台`：`apps/admin`
- `控制面`：`apps/load-control`
- `内置样例目标系统`：`apps/api`

因此这份文档更适合作为历史背景，而不是当前交接入口。
