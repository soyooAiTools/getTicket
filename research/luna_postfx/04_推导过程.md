# 推导过程

## 结论 1
Luna 不能被当作“支持完整 Unity 后处理”的目标平台。

### 依据
- 官方 URP 支持页写明 `Post Processing: No`
- 官方 Post Effects 页仅列出 `SSAO` 和 `CSS filters`
- 本地 `config.json` 中唯一显式 postprocess 配置也是 `ssao`

### 推导
因此，“把 Bloom / DOF / Motion Blur / Chromatic Aberration 直接带到 Luna”不是主路线，只能做：

1. 官方支持项
2. 近似替代
3. 产物层模拟

## 结论 2
打包前扩展是首选，且存在官方支持入口。

### 依据
- Dev Environment 的 Post effects 配置会持久化到最终构建
- 官方支持 `Bridge.Script.Write()`
- 官方支持 External JS Libraries

### 推导
比起打包后硬改 HTML，更稳的方案是：

1. 在 Unity 工程阶段接入 `luna-postfx.js`
2. 用 C# 或配置字段驱动 JS 层效果
3. 只有在最终广告网络要求下，再对导出 HTML 做最小补丁

## 结论 3
很多“想要的后处理效果”应改造成替代实现，而不是继续追求原版 Volume 效果。

### 依据
- Render Objects 明确适合 Outline / Silhouette / X-Ray
- CSS Filters 天然适合全局色调
- HTML Overlay 天然适合暗角、噪点、扫描线

### 推导
应按效果类型拆分实现方式，而不是试图找一个万能后处理框架。

## 结论 4
打包后扩展是可行的，但应该尽量做“独立附加层”，不要碰 Luna 内核。

### 依据
- 用户样本 HTML 保留了 `#application-canvas`
- MDN 说明 `filter` 可直接作用于元素
- 样本产物并未保留所有模板内部滤镜关键字

### 推导
打包后正确姿势是：

1. 找到 `#application-canvas`
2. 对 canvas 或其外层 wrapper 注入 style / overlay
3. 不依赖内部未公开钩子
4. 不修改核心初始化流程
